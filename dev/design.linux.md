# Design of recursive watches on Linux

A recursive watch on Linux is implemented in user space, see "Key differences"
in `docs/platform-differences.md`. This note records the design of the
problems that come from it, and the options considered.

## Design goals

In order of priority:

1. No create or move event is missed. A consumer that applies the events in
   order knows every entry of the tree. A duplicate event, or a missing event
   of another kind, is acceptable.
2. Scalability to large trees. Starting a watch, or a move of a large tree,
   does not overflow the kernel event queue. The tree is limited only by
   `max_user_watches`, the memory used is proportional to the number of
   directories, and a scan is streamed, not collected.
3. A kernel queue overflow is reported by `isEventsLost`, and the stream
   ends at that point. The application opens a new watch.
4. A recursive watch is not led outside its tree by a symbolic link.
5. A watch runs indefinitely without leaking fds, watches or memory.
6. The same streaming API on Linux, macOS and Windows.

## Adding a tree

A recursive watch adds a tree in two steps. `addRoot` adds the watch of a
directory without the open, access and close events, lists the directory,
adds its subdirectories the same way, and then requests these events on the
directory. See `scanFlags`, `addRoot` and `updateWatch` in
`src/Streamly/Internal/FS/Event/Linux.hs`.

### Problem

inotify watches one directory, so adding a tree lists every directory. If the
user enables `setOpened`, `setAccessed` and `setNonWriteClosed`, for example,
by `setAllEvents`, the listing is reported as events. The stream is not read
until the tree has been added, so the events stay in the kernel queue.

Listing an empty directory generates 8 events: 4 on its own watch and 4 on the
watch of its parent. A directory that is listed generates 1 open, 2 access and
1 close events. inotify merges an event only with an identical event just
before it, the copies for the parent separate the 2 access events.

A tree of more than `max_queued_events / 8` directories, 2048 by default,
therefore overflowed the queue when the watch started, with no write to the
tree and no other process involved. The events of the scan were also noise to
the user, nobody had opened those directories.

### Constraint

A directory must be watched before it is listed. A subdirectory created in the
parent then shows up in the listing, as an `IN_CREATE` event, or as both. If
the directory is listed first, a subdirectory created between the listing and
the watch is reported by neither, and it stays unwatched with no indication.
That is worse than an overflow, which reports `isEventsLost`.

### Alternatives

Events counted for trees of about 1000 directories, flat and two levels deep,
with open, access and close events requested:

| Order | Events per directory | Misses a new directory |
|-------|----------------------|------------------------|
| Top-down, add then list (the earlier code) | 8 | No |
| Bottom-up, list, then add and list again | 3 | No |
| Bottom-up, list, then add only | 0 | Yes |
| Two steps, top-down (this design) | 0 | No |

Bottom-up only moves the limit from `max_queued_events / 8` to
`max_queued_events / 3`. The second listing is required by the constraint
above, and a listing of a watched directory generates events.

Filtering the events of the scan in the stream does not work. The events still
fill the kernel queue, and they cannot be told apart from those of another
process.

### Design

* `scanFlags` removes only `IN_OPEN`, `IN_ACCESS` and `IN_CLOSE_NOWRITE`, the
  events that a listing generates. Create, delete, modify and move events are
  requested from the first step, so changes during the scan are reported as
  before.
* `IN_ONESHOT` is deferred too. An event of the scan must not remove the watch.
* Each directory is changed after it and the tree under it are listed. This
  needs no list of the directories. A directory is changed before its parent,
  and the parent still has `scanFlags` while the other subdirectories are
  listed, so a listing reaches no watch with the three events enabled.
* If the two sets of flags are the same, the second step is skipped. This is
  the case for the default events, which pay no extra system call.

### Consequences

* The open, access and close events generated by another process during the
  scan of a directory are not reported.
* The second step takes a path, inotify has no call that takes a watch
  descriptor. The path may have changed after the first step. `updateWatch`
  ignores a path that no longer exists, and removes a watch descriptor that the
  call created for another directory. In both cases the event of the move or
  the deletion, on the parent, brings the map up to date. A watch root that is
  renamed during the scan keeps `scanFlags`.
* Opening a new watch on a tree generates no events. This makes reopening a
  watch a safe response to `isEventsLost`, whatever the size of the tree.

### Not addressed

* A scan of the tree by the application lists directories that have their full
  flags, so it generates 8 events per directory. An application scans the
  tree after an overflow, see "Overflow: the stream ends".
* `addNewDir`, the scan of a directory reported by `IN_CREATE`, reports the
  open, access and close events of the scan. New directories are added as
  their events are read, the queue is drained in between.

## Moves and scans

A directory that arrives by a move, including a rename within the tree, is
scanned after its watch is added. The entries are reported as `isCreated` and
`isScanEvent`, after the `isMovedTo` event. A rename is reported as the tree
leaving and coming back in, see "Every rename leaves the tree and comes back".
`setScanNewDirs False` disables the scan, the directory is still watched.

### Reason for the design

The events are read some time after the operations. A directory can be renamed
before its `IN_CREATE` event is read:

```
mkdir a; touch a/f; mv a b
```

The add of `a` fails, the path no longer exists. The queue then has the same
move events as for a directory moved in, and `f` has no other report. The move
events do not contain the origin of a directory.

The converse is not true either: an `IN_CREATE` event can find a directory
that was moved in.

```
mkdir a; rmdir a; mv /outside/d a
```

`d` contains `f`. When `IN_CREATE` of `a` is read, the path `a` refers to `d`.
The watch of `d` is added and its scan reports `a/f`, an entry that was moved
in, after the `isCreated` event of `a`. The later `IN_MOVED_TO` of `a` scans
it again, see "Order of the scan events".

So neither a create nor a move event tells how a directory arrived when the
event is read. A scan only on `IN_CREATE` is not possible: the scan on
`IN_CREATE` reports entries moved in, and a directory created and moved before
its `IN_CREATE` is read reports its entries only on the move. A directory
created and then moved is equivalent to a directory moved in.

With this design a wrong guess cannot lose an entry, the cost of the rule is an
extra report. A consumer can remove an extra report with `isScanEvent`. A
consumer cannot recover an entry that was not reported
without scanning.

### Designs tried

Each design below was implemented. The code is in the commits named. Commit
`ab65395` has a `Do-Not-Squash` trailer, it is the record of these designs and
must stay in the history.

1. No scan on a move, up to `f84280f`. The reason was that a watch start does
   not report the existing entries, and that a move reports one event on macOS
   and Windows. The program can scan on `isMovedTo`, the watch is added before
   the event is delivered. This lost `f` in the example above for a program
   that scans only on a move from outside the tree.
2. Scan after a failed add, `af20c76`. `MissedDir` recorded a path whose add on
   `IN_CREATE` failed, and the cookie of `IN_MOVED_FROM` carried the record to
   the new path. This needed a list limited to 1024 entries, because no event
   removes an entry in all the cases. The add does not fail if another directory
   is created at the old path, as in `mkdir a; mv a b; mkdir a`.
3. Scan if the old path is reused, `ab65395`. `wpCreated` recorded a path added
   by `IN_CREATE`. `renameDir` scanned `b` if `a` had `wpCreated` and still
   referred to the watched directory. Two cases remained wrong:
   `mkdir a; mv a b; mkdir a; mv b c` lost `c/f`, and with a watched `a`,
   `mv a b; mv b a; mv d b` reported existing entries. The two cases have the
   same state when the first move event is read, so the conditions can fix only
   one of them. Recording `b` fixes the first and makes a watched directory
   renamed away and back report its entries as new. The exact condition is
   whether `IN_MOVED_FROM` was queued before the watch of `a` was added. That
   needs the position of an event in the queue, for example, a count of the
   bytes read and `FIONREAD` at the time of the add.
4. Scan on every move that does not keep the watch. This removes `MissedDir`,
   `wpCreated` and the checks in `renameDir`. A rename that kept the watch
   reported only the entries of the subdirectories that were not watched, a
   consumer had to match the cookies of the move events to move the subtree.
5. Report all the entries on every move of a directory, the current design,
   see "Every rename leaves the tree and comes back".

### Consequences

* The entries of a directory moved in are reported. This differs from a watch
  start, and from macOS and Windows. A program that scans on `isMovedTo` gets
  duplicates. On Linux it does not need its own scan while `setScanNewDirs` is
  enabled.
* A file created in a directory moved in before its move event is read is
  reported, as on macOS and Windows.
* The entries of a moved tree are reported as the walk finds them, the walk
  advances as the stream is read. The memory used by the walk is proportional
  to the depth of the tree. The kernel queue is not read until all the entries
  of the scan have been read. The watches of the tree need a walk of its
  directories in any case.
* A scan can report an entry more than once, see the table.
* A rename of a large tree reports all the entries of the tree, even when the
  rename keeps the watches.
* `setScanNewDirs False` disables the scan on a create and on a move together.
  There is no separate option for moves. Adding the watches of a moved tree
  reads every directory of the tree in either case, so the option would save
  the events reported, not the walk.

### No separate predicate for a scan on a move

The events of a scan on a move and of a scan on a create are both marked by
`isScanEvent` only. An earlier `isMoveScanEvent` was true for an event
generated by a scan that a move event caused. It described the cause of the
scan, not the origin of the entry:

* It was true for `f` in `mkdir a; touch a/f; mv a b`, which is new. A consumer
  that dropped these events had to scan on `isMovedTo` to find `f`, and that
  scan reports the same entries as the scan of the library.
* It was false for `f` in `mkdir a; rmdir a; mv d a`. The `IN_CREATE` event of
  `a` finds the directory moved in, and scans it as a new directory. The test
  is `recScanCreatedFindsMovedIn`.

A consumer could not use it to tell a new entry from one moved in, and dropping
the events was safe only with a scan of its own. It was removed. Marking the
origin exactly has the same problem as design 3.

### Keeping the watch over two renames

Implemented by `renameDir`, `relocatePending` and `takeNamedPending` in
`src/Streamly/Internal/FS/Event/Linux.hs`.

For a watched `a` with watch descriptor W, `mv a b; mv b c` read after both
renames: `b` does not exist when `IN_MOVED_TO` of `b` is read. `probeWatch`
calls `inotify_add_watch` on the new path, and `renameDir` acts on the
result:

| New path | Action |
|----------|--------|
| Refers to W | The paths are changed to the new path, and the tree is scanned |
| Does not exist, or is not a directory | W is kept, its paths are changed to the new path, which is marked pending (`wpPending`). No scan |
| Refers to another directory | The paths of W are removed, and the new path is added as a directory moved in |

The parent of `b` is watched, so every later change at `b` is reported by the
parent. W reports `IN_MOVE_SELF` for every rename of its directory while its
watch exists. A pending path is resolved by the first of these events:

1. `IN_MOVE_SELF` of W: W is the directory that was renamed to `b`, the
   pending mark is removed. `rename(2)` queues `IN_MOVE_SELF` after
   `IN_MOVED_TO`, while it holds the lock of the parent of `b`, so the event
   comes before any later event of `b`. This is the order assumed in the
   IMPORTANT note above `clearMoved`.
2. `inotify_add_watch` on a path `p` returns W: a directory has one path, W is
   at `p`. The pending path and the paths under it are changed to `p`.
3. `IN_MOVED_FROM` or `IN_DELETE` of `b` before `IN_MOVE_SELF` of W: the
   event is for the directory that was renamed to `b`, and W is not that
   directory. The pending path and the paths under it are removed.

In the second and third cases W was added after the rename. It was added on
the `IN_CREATE` or `IN_MOVED_TO` event of a path that was reused before the
event was read, see "Reused paths". In `mkdir a; mv a b; mkdir a`, read
after the second `mkdir`, then `mv b x; mv a z`:

```
IN_CREATE a          the add returns W, the second a
IN_MOVED_FROM a  c1
IN_MOVED_TO b    c1  b does not exist, W is pending at b
IN_CREATE a          the add returns W, W is changed back to a
IN_MOVED_FROM b  c2
IN_MOVED_TO x    c2  x is not watched, it is added and scanned
IN_MOVED_FROM a  c3
IN_MOVED_TO z    c3  the add returns W, W is changed to z
IN_MOVE_SELF W
```

For a watched `a` in `mv a b; mv b c`, `IN_MOVE_SELF` of W follows
`IN_MOVED_TO` of `b`, before `IN_MOVED_FROM` of `b`.

A pending path is not scanned, the path does not exist. The consumer removes
the paths of `a` on `isMovedFrom` of `a` and of `b` on `isMovedFrom` of `b`,
and gets the entries of `c` from the scan after `isMovedTo` of `c`.

Remaining limits:

* If the new path is another directory when `IN_MOVED_TO` is read, as in
  `mv a b; mv b c; mkdir b`, W is removed and added again on `IN_MOVED_TO` of
  `c`. The events other than creations in the tree between the two are lost,
  and the old paths report `isRootUnwatched`. A pending mark is not used here:
  the path of the other directory and the pending path would be equal in the
  map, and the operations on the map that select paths by prefix, for example
  `renamePaths`, cannot tell the two trees apart.
* The events of W read between `IN_MOVED_TO` of `b` and the event that
  resolves the pending path are reported under `b`. In the second case of the
  list above, W was not at `b`.

### Rename between roots

Implemented by `movedInDir`.

A directory moved from one root of a `Watch` to another reports
`IN_MOVED_FROM` with a path in the first root and `IN_MOVED_TO` with a path in
the second. A new path whose root has no path with the cookie is paired with a
path with the cookie whose root has no new path, in the order of the paths.
The pair is handled by `renameDir` as a rename, `renamePaths` changes the root
of the paths. The watches of the tree are kept. A new path that is not paired
is a directory moved in, and a path with the cookie that is not paired is
removed as a directory moved out.

### Order of the scan events

A scan lists the directory after the event that causes the scan is read, and
before the next kernel event is read. Its events are emitted after that event. The kernel events queued after that
event are older than the state the scan read. In
`mkdir a; rmdir a; mv /outside/d a`, with `d` containing `f`, all done before
the events are read:

```
isCreated a
isCreated a/f   isScanEvent    the scan finds d at the path a
isDeleted a
isMovedTo a
isCreated a/f   isScanEvent    a is scanned again
```

`a/f` is reported before the deletion of `a`. A consumer that removes the
paths under a deleted directory removes `a/f`. `rmdir(2)` needs an empty
directory, so this consumer is a natural one, and the model consumer in
`LinuxModel.hs` is one. A watched directory renamed to the path has the same
order: in `mv f/sub a; rmdir a; mv /outside/d a` the scan on `IN_MOVED_TO` of
the rename finds `d` at `a`.

The scan on `IN_MOVED_TO` of `a` reports `a/f` again after the deletion. When
`IN_MOVED_TO` of an already watched path did not scan, `a/f` had no report
after the deletion, and the model test failed in 10 cases at depth 3, all of
these two forms. The test is `recScanCreatedFindsMovedIn`.

A create event has the same order. In `mkdir a; rmdir a; mkdir a; touch a/f`,
the first `IN_CREATE` of `a` adds and scans the second `a`, `a/f` is reported
before `isDeleted` of `a`. The second `IN_CREATE` of `a` finds the path already
watched. It scans the path again and reports `a/f` after the deletion. The test
is `recScanCreatedAgain`.

So every create or move event of a directory reports all the entries under it,
whether the path is already watched or not. The cost is a second report of
the entries of a directory added by an earlier event, for example, a
subdirectory added by the walk of a rename and then reported by its own
`IN_CREATE`.

### Every rename leaves the tree and comes back

Implemented.

Report the entries of a directory on every `IN_MOVED_TO` of the directory,
including a rename within the tree that keeps the watch. A rename is then
always visible to the consumer as the tree going out and coming back in, it is
equivalent to a delete and a create:

* `isMovedFrom` of a directory: the consumer removes the directory and every
  path under it.
* `isMovedTo` of a directory: the consumer adds the directory, the entries
  under it follow as scan events.

The consumer needs no cookie matching and does not wait for the `isMovedTo` of
an `isMovedFrom`. A directory renamed twice, created and moved, or moved in,
is handled the same way. The case above is removed: the `IN_MOVED_TO` of `a`
scans `a` although it is already watched, and reports `a/f` after the
`isDeleted` event of `a`.

This changes what is reported, not what is watched. A rename that keeps the
watch still keeps the watches of the tree. The events of the tree are not
lost, except the open, access and close events while the walk lists a
directory, see `scanFlags`. The walk of a
renamed tree lists every directory already, to find the subdirectories that are
not watched. The extra cost is the events reported, one for each entry in the
tree, on every rename.

### Use cases

`f` is created in `a` or `d` before the first operation shown. `d` is a
directory outside the tree. All the operations happen before the events are
read. "Watched `a`" is a directory created earlier, whose events have been read.
The tests are in `test/Streamly/Test/FileSystem/Event/Linux.hs`.

| Operations | Entries reported | Test |
|------------|------------------|------|
| `mv d a` | `a/f` | `recScanOnMoveIn` |
| `mkdir a; mv a b` | `b/f` | `recScanCreatedThenRenamed` |
| `mkdir a; mv a b; mv b c` | `c/f` | `recScanCreatedRenamedTwice` |
| `mkdir a; mv a b; mkdir a` | `b/f` | `recScanCreatedRenamedPathReused` |
| `mkdir a; mv a b; mkdir a; mv b c` | `c/f` | `recScanCreatedPathReusedRenamed` |
| `mkdir a; mv a ../x` | None | `recScanCreatedThenMovedOut` |
| `mv d a; mv a b` | `b/f` | `recScanMovedInRenamed` |
| Watched `a`: `mv a b`, read before the next operation | `b/f`, the watch is kept | `recScanOnRename` |
| Watched `a`: `mv a b; mv b c` | `c/f`, the watch is kept | `recRenameTwice` |
| Watched `a`: `mv a b; mv b a` | `a/f` | `recScanMovedAwayAndBack` |
| Watched `a`: `mv a b; mv b a; mv d b` | `a/f`, and `b/f` twice | `recScanMovedInAfterMoveAndBack` |

A path that exists only between two renames, `b` in `mv a b; mv b c`, reports
both `isMovedTo` and `isMovedFrom`, in that order, for a new directory, a
watched directory and a directory moved in. These events come from the watch
of the parent and do not depend on the watch of the directory. A program that
applies the move events in order ends with `c` and no `b`. The test is
`recIntermediatePath`.

### Reused paths

A new directory is added on its `IN_CREATE` event, using the path. The operations
below happen before the events are read, so the path refers to a different
directory when the event is read. `f` is a watched directory containing `sub`.
`/out` is outside the tree. `m` is outside the tree and contains `file`. The tests
are in `test/Streamly/Test/FileSystem/Event/Linux.hs`.

| Operations | Behavior | Test |
|------------|----------|------|
| `mkdir d; mv d e; mv f d` | `d` and `d/sub` report each event once, and report `isRootUnwatched` although they stay watched, see below | `recReusedPathMovedWithin` |
| `mkdir d; rmdir d; mv f d` | Each event in the tree of `d` is reported once | `recReusedPathDeleted` |
| `mkdir d; mv f d` | Each event in the tree of `d` is reported once | `recReusedPathReplaced` |
| `mkdir d; mv d /out; mv f d` | `d` and `d/sub` stay watched | `recReusedPathMovedOut` |
| `mkdir d; mv f g; mv d /out; mv g d` | `d` and `d/sub` stay watched, their entries are reported again | `recReusedPathMovedOutRenamedTwice` |
| `mkdir d; mv d /out; mv m d` | `d/file` is reported after `isMovedTo` of `d` | `recReusedPathMovedIn` |
| `mkdir f/new; mv f g; ln -s f f` | The add of `f/new` is ignored, `g/new` is added and reported on the rename | `recParentReplacedBySymlinkLoop` |
| `mkdir f/new; mv f g; ln -s /out f` | `/out/new` is not watched, `g/new` is added on the rename | `recParentReplacedBySymlink` |

How each case is handled:

* `IN_CREATE` of `d` finds the watch descriptor of `f` and adds `d` as its second
  path. `renamePaths` changes `f` to `d` and drops the second path, otherwise the
  map has the path `d` twice and each event is reported twice. Dropping the path
  also drops the cookie recorded in it by `IN_MOVED_FROM` of `d`, which
  `IN_MOVE_SELF` of `f` would take to mean that `f` left the tree.
* A move out has no `IN_MOVED_TO`, so the cookie of `d` can stay in the path. A
  move to a path that has a cookie is a move to a path whose earlier directory
  was moved out. `addMovedDir` removes the cookie and reports the entries of the
  path again. They were reported by the scan on `IN_CREATE`, and the consumer
  removed them on `isMovedFrom`.
* `IN_DONT_FOLLOW` covers only the last component of a path, a symbolic link in
  place of a parent would be followed. A subdirectory is opened with `openat`
  and `O_NOFOLLOW`, and the watch is added on `/proc/self/fd/N`. Checking the
  components and then adding the watch with the path would leave a gap. If
  `/proc` is not mounted (`ENOENT`) or access to it is denied (`EACCES`), the
  watch is added with the path after the check. A path that fails
  to open, including with `ELOOP`, is treated as a directory that no longer
  exists.
* A directory without read permission also fails with `EACCES` on
  `/proc/self/fd/N`. On `ENOENT` or `EACCES` the link `/proc/self/fd/N` is
  read with `readlink`, which needs access to `/proc` and no permission on
  the directory. The watch is added with the path only if the link cannot be
  read, otherwise the error is that of the directory. Without this check any
  user who can write to a directory in the tree could reach the add by path
  with `mkdir -m 000`, and replace a parent with a symbolic link before the
  call: `mkdir -m 000 u/a/secret; mv u/a u/b; ln -s /outside u/a` watched
  `/outside/secret`.
* A directory reported by an event is opened from its root, one component at a
  time, `openSubdir`. A walk of a tree, at the start of a watch and in a
  scan, opens a subdirectory relative to the `O_PATH` fd of
  its parent, `openDirAt`, one `openat` per directory instead of one per
  component. The walk holds the fd of a directory while it adds the
  subdirectories. On a tree of 28000 directories, depth 5, this reduced the
  start of a watch from 0.86 s to 0.54 s.
* The cost of `openDirAt` is one open fd for each level of the walk that is
  kept open, at most `maxOpenLevels`, see "Deep trees". `openSubdir` holds at
  most two fds at a time.
* The parent fd refers to the directory, not to its path. If the parent is
  moved during the walk, its subdirectories are added under the old path. The
  events are read after the walk, the move event of the parent then removes or
  renames the paths under the old path, `unwatchSubtree` or `renamePaths`.
  Opening by path from the root failed in this case and did not add them.

A directory is listed through an fd, not by its path, `openDirStream`. After
its watch is added through the `O_PATH` fd, the directory is opened with
`O_RDONLY` relative to that fd, or relative to the fd of its parent in a scan,
and read with `fdopendir`. A symbolic link that replaces the directory or a
parent after the watch is added is not followed by the listing. The tests
`recScanDirReplacedBySymlink` and `recScanParentReplacedBySymlink` replace them
when the scan reports the directory, before it is listed.

A directory moved within the tree and replaced by a new directory after its
watch is added is listed through its fd, its subdirectories are added under
the old path. The move events of the directory then rename them to the new
path, and the create event of the new directory adds it. The test is
`recScanDirReplacedByDir`.

Opening a directory for reading generates `IN_OPEN` on its watch and on the
watch of its parent, and closing it `IN_CLOSE_NOWRITE`, an `O_PATH` open does
not. The `O_RDONLY` open is done after the watch has `scanFlags`, and the
flags are restored after the close, so these events are not reported. For
this reason the directory is opened twice, once with `O_PATH` to add the watch
and once with `O_RDONLY` to list it. `fdopendir` in glibc makes two `fcntl`
calls, see `dev/upstream-issues.md`.

Alternative tried: reading the fd with `getdents64` through `syscall`, without
`fdopendir`. On 28000 directories `openWatch` took 0.55 s, against 0.60 s with
`fdopendir` and 0.54 s with `opendir` by path. A move of 14138 directories took
0.29 to 0.34 s against 0.33 to 0.35 s. It needs a C wrapper and a parser of
`struct linux_dirent64` in this package. It is kept on the branch
`getdents64-reader`, to be proposed for streamly-core.

In the first row `isRootUnwatched` is reported for the path `d` of the new
directory, the kernel watch of `f` was not removed. `isRootUnwatched` of a path
does not mean that the path is unwatched at the time it is read. The same
order occurs without a shared watch descriptor. In `mv f /out; mkdir f`, the
`IN_IGNORED` event of the old `f` is queued when `IN_MOVE_SELF` is read, after
the `IN_CREATE` event of the new `f`, so `isRootUnwatched` of `f` is read after
`isCreated` of `f`. The event refers to the directory that was at the path. The
tests `recReusedPathMovedWithin` and `recUnwatchedAfterRecreated` record this
behavior.

### Exhaustive test

`test/Streamly/Test/FileSystem/Event/LinuxModel.hs` runs every valid sequence of
`mkdir`, `rmdir`, `touch`, `rm`, `ln -s`, `rename` and a write to a regular
file in the roots, over a small set of paths.
The set of paths includes a path outside the tree, so a rename covers a move in,
a move out, a move between roots, and a rename over an empty directory or a file.
Each sequence runs before the events are read. A split run does a part of the
sequence after a given number of events is read, for each such number.

The checks, after all the events are read:

* A file created in each directory is reported exactly once for each root that
  reaches the directory, at its path. A directory outside the roots reports
  nothing. This finds a missing watch, a duplicate path and a stale path.
* The open event of that file is reported. This finds a watch left with
  `scanFlags`.
* A consumer that applies the events in order knows every entry of the final
  tree. It matches no cookies: `isMovedFrom` and `isDeleted` remove the path
  and every path under it, `isCreated` and `isMovedTo` add the path. Paths
  that the consumer knows and that no longer exist are allowed, an event can
  report the old path. With `setScanNewDirs False` the consumer also lists a
  directory, as the events are read, on its `isCreated` and `isMovedTo`
  events. The check is off with `setCreated False`, and with
  `setMovedFrom False` and `setMovedTo False`.
* A write to a file is reported as `isModified` at the path of the file at
  the time of the write, once for each root that reaches it, if the
  directory of the file was in the roots at the start and has not left them
  since. A directory created or moved in during the sequence is watched only
  after its event is read, its events before that are not reported. This
  finds a watch removed and added again while its directory stays in the
  roots. A directory that arrives at a path by a move, leaves the path, and
  whose path is then taken by another directory, as in
  `mv f a; mv a b; mkdir a`, loses its watch, see "Remaining limits" under
  "Keeping the watch over two renames". The writes in its tree after it
  arrived at the path are not checked. The test
  "write in a dir renamed twice, middle path reused, is reported" in
  `FileSystem.Event.Behavior` records this case on each platform.
* The stream does not raise an exception or stop.

| World | Purpose |
|-------|---------|
| one root | The default config |
| two roots | Moves between disjoint roots of one `Watch` |
| nested roots | A directory reported for two roots |
| symbolic link to outside | A path replaced by a link to a directory outside |
| small | Few paths, for a greater depth |
| `setScanNewDirs False`, `setCreated False`, `setMovedFrom False` and `setMovedTo False` | The watch does not depend on what is reported |

`FSEVENT_MODEL_DEPTH` and `FSEVENT_MODEL_SPLIT_DEPTH` are the maximum lengths
of a sequence, without and with a split. The defaults, 2 and 0, take 28 seconds
for 2157 cases. A depth of 3 and a split depth of 2 takes roughly 12 minutes
for 51436 cases, most of the time is spent closing the inotify fds, about 10 ms
each. The search found all the bugs fixed in the table above at a depth of at
most 4. Use a depth of 3 and a split depth of 2 or 3 after a change in the
moves or scans, and a depth of 4 with `--match small`.

The search does not cover an overflow, a rename of a root, more than one split,
or concurrent changes by another process during a scan.

## Reading the scan

The walk of a scan is a stream, `scanTree` in
`src/Streamly/Internal/FS/Event/Linux.hs`. It is depth first, using
`StreamK.concatIterateWith`. A directory is listed when the stream reaches it,
the entries are not collected. The memory used is proportional to the depth of
the tree, with one directory fd for each of the first `maxOpenLevels` levels,
see "Deep trees".

The watch of a subdirectory is added before its entry is returned, using an
`O_PATH` fd opened relative to the fd of its parent and closed at once. The
stream of the subdirectory may never be read. When it is read it opens the
directory again for reading, relative to the parent fd, with `S.bracketIO`,
lists it through this fd and holds it until the stream ends. The walk is depth
first, the stream of a subdirectory is read while the stream of its parent is
open, so the parent fd is open.

* The watch of a directory is added before its event is delivered: the
  directory of a kernel event when the event is parsed, a subdirectory found by
  the walk when the walk reads its entry from the listing of its parent.
* The kernel queue is not read until the stream has read all the entries of
  the scan. The open, access and close events of the tree are requested when
  the walk of a directory ends, see `scanFlags`. Those generated by another
  process before that are not reported, and the period lasts as long as the
  consumer takes to read the scan.
* If the entries are not reported, `setScanNewDirs False`, the walk is run to
  the end when the event is parsed.

A `Watch` can be read by more than one stream, one after the other or at the
same time. The events not yet read are kept in the `Watch` as a `Stream`,
in an `MVar`. Each `readEvent`, the step of `eventStream`, takes the
`MVar`, runs `uncons` and puts back the rest. A stream that stops reading in the middle of a scan,
or of a buffer of events read from the fd, leaves the rest to the next
stream.

### Exceptions

The rest of the stream is not a pure value. It refers to the open directories
of a scan in progress, and running a part of it changes the watches and the
map. A stream saved before a step cannot be run again after the step has
failed.

An earlier version restored the stream saved before the step when the step
raised an exception:

* In `mkdir d; touch d/f`, a read that timed out after `d/f` was reported
  had reached the end of the scan of `d` and closed `d` before it waited for
  an event. The next read called `readdir` on the closed directory.
* An exception raised while the first event of a read of the fd was handled
  lost all the events of that read, up to 32 KB of events, with no
  `isEventsLost`.

The step never goes back to an earlier stream:

* The step runs with async exceptions masked uninterruptibly. It blocks only
  on the lock of the watch, which is not held across a blocking call.
* The step does not wait for events. `readEvents` returns the wait as an
  action, the stream returns it as an item, `ItemWait`, and `eventStream`
  runs it after the rest of the stream is saved. An async exception, for
  example, a timeout, interrupts only the wait.
* An `IOException` is returned as an item, `ItemFailed`, by `handleEvent`
  for a kernel event and by the stream of a scan for an entry, `ScanFailed`.
  It is raised after the rest of the stream is saved. The events of the
  kernel event are reported before the exception.
* Any other exception is saved in place of the stream, every later read
  raises it again.

The operation that failed is not tried again. A directory that could not
be added, for example, at the `max_user_watches` limit (`ENOSPC`) or
without a free fd (`EMFILE`), is not watched, and neither is the tree under
it. A scan continues with the next entry.

There is no event for the failure. The read of the stream raises the
`IOException`, and the stream can be read again. The message names the
directory, for example, `add watch: /root/a/b`. The exception does not
tell that the tree under the directory is not watched. A permission error
is not raised, the directory is reported as `isAccessDenied`.

The rest of the handling of that kernel event is skipped, the map can keep
a path that the event would have changed.

The tests are `readAfterTimeout`, `readAfterFailure` and
`readAfterScanFailure`.

## Deep trees

Implemented by `maxOpenLevels`, `walkSubdirs` and `scanChildren` in
`src/Streamly/Internal/FS/Event/Linux.hs`.

A walk keeps a directory open while it walks the tree under it, to continue
the listing and to open the subdirectories relative to its fd. The start of a
watch holds two fds for each level, the
`O_PATH` fd and the directory stream, a scan holds one. The fds grew with the
depth of the tree. With `ulimit -n 64`, a chain of 120 directories moved into
the tree ended the watch with `EMFILE` at a depth of 50. Any user who can
write to a directory in the tree could do the same with a chain of about 1000
directories at the default limit of 1024.

Only the first `maxOpenLevels` levels of a walk, 32, are kept open. A
directory at a deeper level is closed before its subdirectories are walked:

* At the start of a watch, `walkSubdirs` returns the names
  of the subdirectories, and they are walked after the directory is closed.
* In a scan, the stream of the directory returns all its entries first, and
  adds the watch of a subdirectory when its entry is read, as at the other
  levels. After the directory is closed, the stream returns the entries of
  each subdirectory. The entries of a subdirectory at these levels follow the
  other entries of its parent, not the entry of the subdirectory itself.
* A subdirectory of a closed directory is opened from the root, one component
  at a time, `openSubdir`. The time taken is proportional to the depth.

The flags of the directory are changed to `watchFlags` after the trees of its
subdirectories are walked, as at the other levels.

The memory used at these levels is proportional to the number of
subdirectories of a directory, instead of the entries being streamed. Each of
these subdirectories has an entry in the map as well.

A walk holds at most 67 fds at the start of a watch, and 35 in a scan. The
tests are `recDeepAtStart` and `recDeepMovedIn`, on a chain of 300
directories with a limit of 256 fds.

## Path index

Implemented by `WdMap`, `PathKey` and `subtreeWds` in
`src/Streamly/Internal/FS/Event/Linux.hs`.

The map of a watch is keyed by the watch descriptor. A rename of a directory
changes the paths of its tree, and a directory moved out removes them. The
cookie of `IN_MOVED_FROM` is recorded in the path of the moved directory, and
`IN_MOVED_TO` finds the paths with the cookie. Each of these visited every
watch descriptor of the map, and rebuilt the map. On a watch of 24200
directories, 2000 renames of an empty directory took 27.0 s, 13.5 ms for
each, and 2000 `rmdir` took 1.8 s. On 2100 directories they took 2.9 s and
0.15 s. The kernel queue is not read while an event is handled, so 74
renames of a directory in a second were enough to fall behind.

`WdMap` keeps three indexes with the map:

* The watch descriptors of each path, a `Data.Map` keyed by `PathKey`.
* The watch descriptors that have a path with a cookie.
* The watch descriptors that have a pending path.

Only `insertWdUser`, `insertMarker` and `deleteWd` change the map, they update
the indexes. The other operations find the watch descriptors to change
through an index.

`PathKey` orders the paths by the subdirectory path and then by the root. The
subdirectory paths are compared bytewise with `/` ordered before any other
byte, so that a directory is followed by the paths under it: `a/b`, `a/b/c`,
`a/b-c`. In the plain bytewise order `a/b-c` comes between `a/b` and `a/b/c`.
The tree of `a/b` is the range of keys from `a/b` up to `a/b` followed by the
byte 1. The range includes the same subdirectory path in other roots, the
callers select the paths with `isInSubtree`. The root is compared last, most
of the paths of a watch have the same root.

With the index the same 2000 renames take 0.40 s and the 2000 `rmdir` 0.10 s,
on both trees.

Costs, on a tree of 28257 directories:

* 72 bytes for each path: 48 for the node of the `Data.Map` and 24 for the
  `IntSet`. The key is the `PathRep` of the path in the map, not a copy. The
  live heap after the start of the watch is 8.7 MB, it was 5.9 MB.
* The start of the watch takes 0.78 s, it took 0.67 s.

The comparison of `PathKey` is `OPAQUE`. When it was inlined, the insert of
the `Data.Map` took the key unboxed and allocated a new tuple to store it,
24 more bytes for each path.

A move out of 14128 directories no longer builds a second map. The maximum
residency during the move out was 13.7 MB, it stays at 9.7 MB, which is
reached at the start of the watch.

## Symbolic link roots

With `setFollowSymLinks False`, the kernel watch of a root that is a symbolic
link is on the link itself. The root is opened with `O_NOFOLLOW` in that
case, `openDirAt`, and is handled as a root that is not a directory: its
target is not listed. Earlier the root was opened without `O_NOFOLLOW`, and
in recursive mode the subdirectories of the target were watched while the
target itself was not. The test is `recRootSymlinkNoFollow`.

## Renamed roots

Implemented by `unwatchGoneRoots` in `src/Streamly/Internal/FS/Event/Linux.hs`.

A kernel watch belongs to an inode, a renamed root stays watched by the kernel.
Its events would report the old path, which no longer exists or refers to
another object, and the kernel does not report the new path. On `IN_MOVE_SELF`
the root and the paths under it are removed and report `isRootUnwatched`, in
both modes. `IN_MOVE_SELF` is requested for every root, and is not reported
unless `setRootMoved` is enabled. macOS watches the path, a renamed root is not
watched there either.

The root is removed only if its path no longer refers to the watched object
when the event is read. Two hard
links watched as roots share one watch descriptor, and the rename of one link
reports `IN_MOVE_SELF` for both. A root renamed back before the event is read
stays watched.

The `IN_MOVE_SELF` or `IN_IGNORED` event of a root can be dropped in an
overflow. The stream ends on the overflow, see "Overflow: the stream ends".

## Subdirectory without permission

Implemented by `ignoreInvalidOrInaccessible` in
`src/Streamly/Internal/FS/Event/Linux.hs`.

`inotify_add_watch` needs the read permission on a directory, and listing it
needs the read and the search permissions. A subdirectory that fails with
`EACCES` or `EPERM` is skipped and reported as `isAccessDenied`, the rest of
the tree stays watched. A watch root without permission raises an exception,
because the caller named the root and nothing under it can be watched.

Reasons:

* Raising an exception ended the watch of the whole tree. Any user who can
  write to a directory in the tree could end the watch with `mkdir -m 000`.
* The `find` command and `defaultReadOptions` of streamly-core skip an
  unreadable directory and continue.
* On macOS the watch reports events inside a root without read permission,
  see the table in `docs/platform-differences.md`.

There is no config option. A consumer that needs the whole tree, such as a
backup tool, can raise an exception on the `isAccessDenied` event. A silent
skip is not an option, the consumer would not know that a part of the tree is
not watched.

A subdirectory denied while the event stream handles an event is returned by
the scan or the walk as a value, `ScanDenied` in the stream of a scan and a
list of paths from `addToWatchAt`, and is reported in the
events of that kernel event. An `isAccessDenied` event follows the create or
move event of the directory, at the point of the scan where the directory was
found.

A subdirectory denied by `addRoot` or `openWatch` is recorded in a queue in
the `Watch`, the call runs in another thread or before the stream exists.
`readEvents` takes the queue with each read of the inotify fd, under the lock
of the `Watch`, and the queued events are reported before the kernel events
of that read. The same queue reports the `isRootUnwatched` events of a
`removeRoot` without `/proc`, see "Removal without /proc".

`ENOSPC` from the `max_user_watches` limit still raises an exception.
Skipping it would drop more and more of the tree without a clear limit.

The subdirectory is not added again when its permissions change. Its parent
reports `IN_ATTRIB` for the change only if metadata events are requested.

## Overflow: the stream ends

Implemented by the `IN_Q_OVERFLOW` case of `handleEvent` in
`src/Streamly/Internal/FS/Event/Linux.hs`.

On an `IN_Q_OVERFLOW` event the stream reports one `isEventsLost` event for
each watch root, closes the watch and ends. The events read before the
`IN_Q_OVERFLOW` event are reported as before. The events after it, in the
same read and in the kernel queue, are discarded with the fd. The same
happens in recursive and non-recursive mode.

### Recovery by the application

After the `isEventsLost` events the stream ends. The application recovers in
one of two ways:

* In the same process: open a new watch on the same roots, for example by
  running `watchWith` again, and then scan the tree to find the changes made
  since the last event it read. The watch is opened before the scan, so that
  a change made during the scan is reported by the watch, the scan, or both.
  The other state of the process is kept.
* By a restart of the process: exit, and let the service manager, for
  example systemd with `Restart=on-failure`, start the program again. The
  program scans the tree at its start as usual. The service manager also
  limits the rate of restarts under sustained load.

Opening a watch on a tree generates no events, see "Adding a tree", so a new
watch does not overflow the queue by itself. A scan of the tree by the
application with open, access and close events enabled generates 8 events
per directory, see "Consequences" below.

### The kernel queue after an overflow

The kernel keeps at most one `IN_Q_OVERFLOW` event in the queue of an inotify
fd. While that event is queued, an event that does not fit in the queue is
dropped and no other `IN_Q_OVERFLOW` event is queued. A read of the fd
returns at most 32 KB, about 1000 events, and makes room in the queue. The
events generated after the read are queued after the `IN_Q_OVERFLOW` event,
and the queue can fill up again before the `IN_Q_OVERFLOW` event is read.
The events read after an `IN_Q_OVERFLOW` event can therefore have gaps, and
no event reports a gap.

Measured on Linux 6.12 with `max_queued_events` of 16384: 16884 files were
created in a watched directory, one read returned 1024 events, and 1524 more
files were created. The queue then had 15360 events, one `IN_Q_OVERFLOW`
event, and the create events of the first 1023 of the 1524 files. The other
501 create events were dropped without a second `IN_Q_OVERFLOW` event.

An event dropped after the `IN_Q_OVERFLOW` event is read queues a new
`IN_Q_OVERFLOW` event. So the gaps are in the events generated before the
`IN_Q_OVERFLOW` event is read. There is no point in the event stream after
which the events are complete, until the application looks at the file
system again.

### History: the soft restart

Earlier, `setRestartOnOverflow`, enabled by default, restarted a recursive
watch in place after an overflow. `restartTree` added the tree of each root
again, on the thread reading the stream:

* `inotify_add_watch` without `IN_MASK_ADD` replaced the flags of each
  directory with `scanFlags`, the directory was listed, and its flags were
  restored. The call returned the existing watch descriptor of a directory,
  the map was built again from the results.
* A directory found by the walk and not in the map was reported as
  `isCreated` with `isScanEvent` true. A path in the map that the walk did
  not find was removed and reported `isRootUnwatched`.
* A root whose path no longer had its watch descriptor was removed.
* A marker was queued for the removals whose `IN_IGNORED` event may have
  been dropped, `syncRemovals`.

Earlier still, `setRescanOnOverflow` listed the directories with their full
flags, and added only the missing directories. With open, access and close
events enabled this generated 8 events per directory, and a tree of more
than `max_queued_events / 8` directories caused the next overflow without any
other activity.

Events counted on a flat tree of 1001 directories, with open, access and close
events requested:

| Method | Events |
|--------|--------|
| Rescan with the full flags | 8003 |
| In place: replace the flags, list, restore the flags | 0 |
| Remove all the watches | 1001 `IN_IGNORED` |
| Add the tree again after removing all the watches | 0 |

The in-place restart queued no events, kept the watch descriptors, and had no
size limit. On a tree of 20000 directories with open, access and close events
enabled, a burst that overflowed the queue caused one restart and one
`isEventsLost` event for each root.

### Problems of the soft restart

The restart kept the fd, its queue and the map, and tried to bring them up
to date. These problems were found:

1. **Renames across a gap.** After the restart the stream handled the events
   that were queued before the walk, and these events have gaps. A rename is
   tracked over three events, `IN_MOVED_FROM`, `IN_MOVED_TO` and
   `IN_MOVE_SELF`, and a gap can drop any of them. For a watched `a` with
   watch descriptor W, in `mv a b; mv b a`, the queue after the
   `IN_Q_OVERFLOW` event had the three events of the first rename, and the
   three events of the second rename were dropped. The walk found `a`. Then:

   ```
   IN_MOVED_FROM a  c1  the cookie c1 is recorded in a
   IN_MOVED_TO b    c1  b does not exist, the paths of a are changed to the
                        pending path b
   IN_MOVE_SELF W       the pending mark is removed
   ```

   No later event changed the paths back, and the events of the tree of `a`
   were reported under `b`. The stress test "the tree is watched after
   overflows that repeat while it changes" renames a tree of 111 directories
   and back in each round. It failed once in about 35 runs, with 111
   directories reporting their events at the wrong path. In 6 runs of the
   test, 10 of the 72 restarts had such a gap between two renames of that
   tree.

   A fix recorded the end of the queued events before the walk, with
   `FIONREAD`, and did not track a rename with an event before that point.
   It depended on counting every byte read from the fd and handled by the
   stream exactly once; an event lost or handled twice would shift the
   point for every later overflow.

2. **The consumer gets the same wrong tree.** Even with that fix, the events
   generated before the walk were reported after the events of the restart.
   A consumer that applies the events in order, in the example above, removes
   `a` on `isMovedFrom` and adds `b` on `isMovedTo`. No later event brings
   `a` back. Not reporting these events was the next proposal.

3. **A path taken by another directory.** The walk removed a path of the map
   only if it did not find the path, it did not compare the watch
   descriptors. After `mv dir z; mv dir2 dir` during an overflow, the watch
   descriptor of the first directory had the paths `dir` and `z`, and a file
   created in `z` was reported twice, as `dir/file` and as `z/file`.
   A directory deleted during the overflow, whose `IN_IGNORED` event was
   dropped and whose path was created again, kept a dead entry in the map the
   same way.

4. **State from before the overflow.** Pending paths, the cookies of
   renames, removal markers and paths marked removed were kept and had to be
   reconciled with the walk. A root renamed during the overflow was detected
   by comparing its watch descriptor.

5. **Failures not reported.** A failure of `unwatchPaths` in the restart was
   discarded, a removed path could miss its `isRootUnwatched` event or keep
   its kernel watch.

6. **Files are not restored.** The restart reported the directories only. A
   file created, modified or deleted during the overflow was not reported, so
   a consumer that needs the files has to scan the tree after `isEventsLost`
   anyway.

7. **Cascading overflows.** The walk ran on the thread reading the stream,
   and the kernel queue was not read during the walk. Activity by other
   processes that generated more than `max_queued_events` events during the
   walk caused another overflow and another restart, until the activity
   slowed down. Each restart walked the whole tree again, and each new
   overflow could leave gaps in the events after it, as in problem 1.

   The stress test "the tree is watched after overflows that repeat while it
   changes" overflows the queue and then changes the tree for 10 seconds
   while the consumer reads. A restart of a tree of 2000 directories took
   less time than one of 10000 directories, and more overflows followed each
   other, 33 against 14 in one run.

   A removed path stays in the map until the `IN_IGNORED` event of its watch
   descriptor, or of a marker listing it, is read, and the overflow could
   drop these events. `syncRemovals` queued a new marker on each overflow,
   listing the markers whose `IN_IGNORED` event had not been read and each
   path marked removed. During cascading overflows the `IN_IGNORED` event of
   each marker was dropped by the next overflow, and the markers
   accumulated. A marker did not copy the paths listed in the older markers,
   copying their lists would double the list with each marker.

### Alternative: reopen the fd inside the library

On an overflow, close the inotify fd, open a new one and add the tree to it,
as `openWatch` does. This solves problems 1 to 4: the queue with the gaps
goes away with the old fd, the map starts empty, and every event read from
the new fd was generated after its directory was watched. The restart is the
same code as the start of a watch.

It leaves these problems:

* `watchFd` is fixed for the life of a `Watch`. It would have to become
  mutable under the lock of the watch, read by `withWatchFd` and by the
  registration of a wait.
* `dup2(new, old)` keeps the fd number, but in the threaded RTS a thread
  waiting on the old file loses its epoll registration, and is not woken up.
* In the non-threaded RTS, `select` fails with `EBADF` if a waited fd is
  closed, and the RTS terminates the program. The swap has to wait for the
  waiting threads as `closeWatch` does.
* Both fds holding the watches of the tree count twice against
  `max_user_watches`, a large tree fails with `ENOSPC`. The old fd has to be
  closed before the walk.
* The watch descriptors of the two fds cannot be compared. The added and
  removed directories have to be reported by comparing paths, and a renamed
  root is lost at its new name.
* State that does not belong to the old fd has to be sorted: the bytes read
  from the old fd and not yet handled are dropped, the synthetic events
  queued by other threads are kept, a root removed by the user still needs
  its `isRootUnwatched`.
* An async exception after the close and before the end of the walk leaves
  the watch half built. The restart has to be repeatable.
* `addRoot` and `removeRoot` from another thread during the walk
  either wait for the walk, holding the lock, or have to be merged into the
  new map.

Problem 6 remains. The walk of the new fd also runs on the reader, and
cascading overflows repeat the reopen as in problem 7, without the
accumulated markers.

### Choice

The stream ends, and the application opens a new watch. Reasons:

* After `isEventsLost` the application has to scan the tree anyway, the
  files changed during the overflow are not reported by any restart.
* Opening a new watch in the application gives the same result as the
  reopen inside the library: a new fd, an empty map, and a queue without
  gaps. `closeWatch` and `openWatch` already handle the waiting threads and
  the concurrent calls.
* A daemon can exit on `isEventsLost` and be restarted by its service
  manager, which also limits the rate of restarts under sustained load.
* The restart code, `restartTree`, `syncRemovals` and the root checks of an
  overflow, is removed with its problems.

### Consequences

* The events after the `IN_Q_OVERFLOW` event are not reported, including the
  ones the kernel queued without a gap. `isEventsLost` reports that events are
  missing from that point.
* The events between the overflow and the start of the new watch are lost.
  The application finds the changes by its scan of the tree.
* A scan by the application lists directories that have their full flags,
  and generates 8 events per directory if open, access and close events are
  enabled, see "Not addressed" under "Adding a tree". A scan of the tree by
  `openWatch` itself would avoid this, see "Reporting existing entries when
  a watch starts" in `dev/design-issues.md`.
* Under sustained activity the application opens new watches repeatedly,
  each one walks the whole tree.

## Removal without /proc

Implemented by `addRemovalMarker` in `src/Streamly/Internal/FS/Event/Linux.hs`.

A marker is a watch on a pipe, added via `/proc/self/fd/N`. If `/proc` is not
mounted or access to it is denied, `queueIgnored` returns `False` and no
marker is queued. The removed paths of the shared watch descriptors, and the
markers that would have been listed, are then removed from the map at once,
and `addRemovalMarker` returns the removed paths. `removeRoot` puts their
`isRootUnwatched` events in the queue of the `Watch`.

* The events already in the kernel queue for a removed path are not reported
  for it. The events of the other paths of the watch descriptor are reported
  as before.
* `isRootUnwatched` of a shared path is reported before the `IN_IGNORED` of a
  watch descriptor removed in the same call, and before the events already in
  the kernel queue, including an overflow. The events already read from the
  fd and not yet reported are reported before it, the queue is taken with
  the next read.
* A removal from another thread wakes up the reader. In the threaded RTS the
  reader waits for the fd `orElse` a non-empty queue, a read that returns no
  kernel events then reports the queue. In the non-threaded RTS the queue is reported after the
  next read of the fd. The queue is a `TVar` for this reason.
* The events of each read of the fd are parsed on their own, after the
  queued events taken with the read. A read of an inotify fd returns whole
  events.
* The removals inside the stream, `unwatchSubtree` and `unwatchGoneRoots`,
  use the same fallback, so a move of a root without `/proc` does not raise
  an exception in the stream.
  They return the removed paths to `readOneEvent`, which reports their
  `isRootUnwatched` events after the events of the kernel event that caused
  the removal and the entries found by its scan, not through the queue.

A marker on a new temporary directory instead of a pipe would keep the order
of the events. It was not used: a user path, for example a recursive watch of
the parent of the temporary directory, can share the watch descriptor of the
marker.

`test/no-proc.sh` runs the Linux test suite in a user and mount namespace,
with a tmpfs over `/proc`, and with a tmpfs of mode 000 and the capabilities
dropped. The tests that count fds through `/proc` are pending in these runs.
